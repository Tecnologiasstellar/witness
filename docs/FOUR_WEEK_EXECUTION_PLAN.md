# Four-week execution plan

Build window: 2026-08-21 through 2026-09-17  
Shipathon deadline: 2026-09-30 at 11:45 p.m. PDT

## Goal

Reach a public App Store release by September 17 with sufficient time for repair, measured real-user feedback, build-in-public evidence, and the final Devpost submission.

## Weekend zero — A reviewable ritual (Aug 21–23)

The weekend goal is not a broad scaffold. It is one beautiful, locally working experience that can be shown on an iPhone or in a faithful preview by Sunday evening.

### Friday, Aug 21 — Structure and visual language

- Scaffold the native SwiftUI project and test target.
- Implement the four-tab shell with Today as the default; Archive, Witnessed, and Settings may use intentional preview states.
- Establish the system-serif/system-sans type hierarchy, warm-paper/ink/lichen palette, spacing, corners, dividers, and light/dark foundations.
- Encode one schema-valid flagship species fixture using rights-safe temporary geometry/gradient art only.

### Saturday, Aug 22 — Complete the vertical ritual

- Build the image-first Today screen with overlapping editorial sheet.
- Implement story, Witness-once interaction, local count state, action card, evidence drawer, private reflection, and share preview.
- Persist Witnessed state and show the species in the personal deck.
- Add deterministic tests for catalog validation, day assignment, witness idempotency, and streak calculation.

### Sunday, Aug 23 — Polish and evidence

- Refine loading, empty, offline, completed, and reduced-motion states.
- Validate Dynamic Type, VoiceOver labels/order, contrast, touch targets, and dark appearance.
- Produce a short screen recording or screenshot sequence of the complete local flow.
- Record defects, decisions, and the exact week-one continuation point.

### Sunday showable definition

A reviewer can understand Witness without explanation and complete:

`Open -> meet today's species -> read -> Witness -> see confirmation -> take an action -> view evidence -> save a private reflection -> find the card in Witnessed`.

The weekend build may use a clearly labeled local count and temporary owned artwork. It must not contain copied DailyArt screenshots, fabricated live data, unverified production facts, or a pretend purchase/backend.

## Week 1 — Prove the ritual (Aug 21–27)

### Product

- Lock MVP scope, visual direction, launch audience, and impact claims.
- Build one complete species content card with verified sources, action, and media rights.
- Test the one-sentence pitch and a clickable ritual prototype with 5–8 people.

### Engineering

- Create native SwiftUI project, test targets, build configurations, and CI-safe structure.
- Implement bundled catalog validation and one complete vertical slice:
  `Today -> story -> Witness -> local deck -> action -> sources -> share preview`.
- Implement local persistence, deterministic daily assignment, accessibility foundations, and offline behavior.
- Add purchase and backend protocol seams, but do not block the slice on hosted accounts.
- Use the audited DailyArt references for interaction hierarchy only; follow the Witness-specific visual system and anti-copy constraints.

### Operations

- Create App Store Connect app record, bundle ID, RevenueCat project, and Supabase project.
- Confirm Paid Apps Agreement, tax, and banking status.
- Register/join Shipathon and begin a concise #BuildInPublic log.

### Exit gate

One real species completes the entire ritual on a physical iPhone with no placeholder facts, art, legal URL, or action link. Core tests pass.

## Week 2 — Make it real (Aug 28–Sep 3)

### Product/content

- Expand to 14 launch-ready species using the locked schema.
- Run copy, scientific, action, and media-rights review per card.
- Conduct usability test round two; incorporate only evidence-backed changes.

### Engineering

- Deploy idempotent witness-event and aggregate-count backend.
- Add offline queue/retry and honest count states.
- Integrate RevenueCat Test Store, then App Store products and entitlement.
- Build Witness+ paywall, full-archive gate, restore flow, and purchase-state tests.
- Implement local reminders and share-card export.

### Exit gate

Fresh install, offline ritual, sync, purchase, restore, and expiry behavior pass in controlled test environments. All 14 records pass catalog validation.

## Week 3 — Release candidate (Sep 4–10)

### Product

- Freeze features.
- Finish icon, screenshots, preview copy, privacy policy, terms, support, and content-corrections path.
- Run a small beta and collect structured impact/clarity feedback.

### Engineering/QA

- Test App Store Sandbox purchase on physical device.
- Test the full daily loop across supported device sizes, Dynamic Type, VoiceOver, Reduce Motion, offline/slow network, date/timezone changes, relaunch, and fresh install.
- Add crash/error telemetry with privacy disclosure.
- Run performance, memory, network-failure, and content-integrity checks.
- Upload first TestFlight build no later than September 6.

### Exit gate

No P0/P1 defects. Physical-device ritual and App Store Sandbox purchase/restore are independently evidenced. App privacy answers match actual SDK/data behavior.

## Week 4 — Submit and launch (Sep 11–17)

### Release

- Submit the App Store candidate by September 15, earlier if green.
- Respond to App Review immediately; make only blocker-level changes after submission.
- Manually release by September 17 when approved.

### Competition

- Record a rights-safe, device-captured demo under two minutes.
- Draft the Peace Prize impact/feasibility narrative with real metrics and explicit limits.
- Prepare 1024×1024 icon and at least one 1179×2556 screenshot without a device frame.
- Provide trial/promo access and complete English testing instructions.
- Continue build-in-public posts showing user feedback and changes, not vanity updates.

### Exit gate

The app is publicly downloadable in the United States, the RevenueCat-powered purchase works, all Devpost materials are complete, and every claim in the demo matches the public build.

## Buffer — Review, traction, final submission (Sep 18–30)

- Resolve App Review issues and ship a small corrective update if necessary.
- Track installs, completed witnesses, return rate, action opens, shares, trial starts, and qualitative feedback.
- Publish focused build-in-public retrospectives and show which feedback changed the app.
- Submit Devpost at least 24 hours before the deadline.

## Daily operating rhythm

1. Select one vertical outcome.
2. Define acceptance evidence before implementation.
3. Make the smallest reversible change.
4. Run focused tests, then build/device validation proportional to risk.
5. Update the decision log and release gate status.
6. Capture one honest build-in-public artifact when there is something learned.
